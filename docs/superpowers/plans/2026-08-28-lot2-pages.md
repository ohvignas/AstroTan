# Lot 2 — Pages : Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un éditeur crée une page composée de blocs dans le dashboard, la prévisualise sans qu'elle soit publique, la publie, et elle apparaît sur le site Astro en moins de cinq secondes.

**Architecture:** Les blocs sont un champ embarqué validé par une union discriminée Convex, rendus **uniquement** en `.astro` via un registre exhaustif. Le site est en SSG avec SSR sélectif et cache par tags (Astro 7). La publication invalide ces tags par un outbox transactionnel avec cron de rattrapage, parce que les actions planifiées Convex ne sont pas retentées.

**Tech Stack:** Astro 7.2.8 · @astrojs/node 11.1.4 · Convex 1.45.0 · TanStack Start 1.168.49 · Tailwind v4 · Vitest + convex-test

**Spec:** `docs/superpowers/specs/2026-08-27-astrotan-design.md` (sections 4, 6)

## L'invariant du lot

> **Une page non publiée n'est visible que par un porteur de jeton de prévisualisation valide, et une page publiée apparaît sur le site sans rebuild.** Aucune query publique ne peut servir un brouillon, quel que soit l'identifiant qu'on lui passe.

```ts
// convex/blocks.ts
import { v } from "convex/values"

const ctaValidator = v.object({ label: v.string(), href: v.string() })

export const blockValidator = v.union(
  v.object({ type: v.literal("hero"), title: v.string(), subtitle: v.optional(v.string()), mediaId: v.optional(v.id("_storage")), cta: v.optional(ctaValidator) }),
  v.object({ type: v.literal("richText"), html: v.string() }),
  v.object({ type: v.literal("features"), items: v.array(v.object({ title: v.string(), body: v.string() })) }),
  v.object({ type: v.literal("gallery"), mediaIds: v.array(v.id("_storage")) }),
  v.object({ type: v.literal("faq"), items: v.array(v.object({ question: v.string(), answer: v.string() })) }),
  v.object({ type: v.literal("cta"), title: v.string(), cta: ctaValidator }),
)
export type Block = typeof blockValidator.type
export const BLOCK_TYPES = ["hero", "richText", "features", "gallery", "faq", "cta"] as const
```

- [ ] **Step 5: Borner les champs texte.** `title` et les champs de blocs doivent avoir une longueur maximale — le lot 1 a livré deux fois des champs non bornés qui atterrissaient dans une interface.

### Task 2: Queries publiques et queries de prévisualisation — familles séparées

**Files:** `convex/pages.ts`, `convex/lib/previewToken.ts`, leurs tests

**L'invariant de sécurité central du projet.** Les queries publiques n'acceptent aucun jeton et filtrent `status === "published"` en dur. Les queries de prévisualisation sont une **famille de fonctions distincte** qui revérifie un HMAC côté Convex.

- [ ] **Step 1: Tests d'abord, sur les chemins malheureux** — une query publique appelée avec l'id d'un brouillon renvoie `null` ; un jeton expiré, altéré d'un octet, ou émis pour une autre page est refusé.
- [ ] **Step 2: Vérifier les échecs.**
- [ ] **Step 3: HMAC de prévisualisation** — SHA-256 de `{type}:{id}:{exp}` avec `PREVIEW_SECRET`, expiration 15 minutes, comparaison en temps constant.
- [ ] **Step 4: `getPublishedPage(slug)` et `listPublishedPages()`** — filtre en dur, aucun paramètre de jeton.
- [ ] **Step 5: `previewPage({ id, token })`** — revérifie le HMAC ; ne partage aucun code de lecture avec la famille publique.
- [ ] **Step 6: Test paramétré** sur la liste des queries publiques : chacune, confrontée à un brouillon, doit rendre vide. C'est le garde-fou qui empêche qu'une septième query publique oublie le filtre.
- [ ] **Step 7: Commiter.**

### Task 3: Publication et outbox d'invalidation

**Files:** `convex/pages.ts` (modifier), `convex/revalidate.ts`, `convex/crons.ts`, tests

- [ ] **Step 1: Tests** — `publishPage` insère la ligne d'outbox **dans la même mutation** ; un échec HTTP incrémente `attempts` et repousse `nextAttemptAt` ; six échecs marquent `failed` ; le cron reprend une ligne dont l'action planifiée a été perdue.
- [ ] **Step 2: Vérifier les échecs.**
- [ ] **Step 3: Table `revalidationOutbox`** — `tags[]`, `status`, `attempts`, `nextAttemptAt`, `lastError?`, `createdAt` ; index `by_status_next_attempt`.
- [ ] **Step 4: `publishPage`** — `requireRole(["owner","admin"])`, écrit statut et `publishedAt`, insère l'outbox, planifie `internal.revalidate.drain`.
- [ ] **Step 5: `drain`** — réclame les lignes dues, POSTe sur `${SITE_URL}/api/revalidate` avec `x-revalidate-secret`, backoff 1 s / 5 s / 25 s / 2 min / 10 min.
- [ ] **Step 6: Cron de rattrapage** à 60 s.
- [ ] **Step 7: Déclarer au registre, commiter.**

**Piège connu, hérité du lot 1 :** `ctx.scheduler.cancel` sur une **action** déjà terminée jette. Si une révocation ou une dépublication annule un job, lire d'abord `ctx.db.system.get(id)` et n'annuler que `pending` ou `inProgress`.

**Files:** `apps/web/src/pages/api/revalidate.ts`, `apps/web/src/pages/preview/[type]/[id].astro`

- [ ] **Step 1: `/api/revalidate`** — POST uniquement, `context.cache.set(false)`, comparaison **en temps constant** de `x-revalidate-secret`, puis `context.cache.invalidate({ tags })`.

**Dette assumée à documenter dans le code :** `memoryCache()` est par processus. L'invalidation ne touche qu'une instance. Le lot tourne à **un seul réplica** de `web` ; passer à N imposera un provider partagé.
